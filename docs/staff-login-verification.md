# Staff login verification

Staff accounts named `staff1` and `staff2` must submit a fresh browser location with every password login. The login request checks the reported coordinates on the server against latitude `12.8821489`, longitude `80.0808760`, and a fixed 200 metre radius. GPS accuracy must be present and within the configured accuracy threshold. The login route is rate limited, and each accepted or rejected location check is recorded in `attendance_verification_attempts` with its business timestamp, coordinates, accuracy, calculated distance, decision, and reason.

The first login on each Asia/Kolkata calendar date also requires a camera capture before staff routes are available. Later logins that day still require GPS but reuse that day's selfie. The next business date requires a new capture. Weekly-off status does not bypass login checks; a first-login selfie on a weekly-off date leaves the attendance status as `weekly_off`.

The selfie form uses the browser camera API and has no gallery upload control or file-upload route. A web browser cannot provide cryptographic proof that an image came from a live camera. Similarly, browser/device coordinates and reported accuracy are not cryptographically trustworthy: a rooted or modified device, developer tools, a mock-location provider, or a crafted HTTP request can spoof them. Server-side distance calculation, accuracy limits, login throttling, authenticated account matching, and audit records reduce casual bypasses and improve reviewability, but they do not eliminate deliberate GPS spoofing or image replay. Stronger assurance would require a trusted managed device or an external identity/liveness service, neither of which is configured in this application.
